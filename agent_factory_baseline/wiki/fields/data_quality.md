# Качество данных

## Назначение и граница цеха
Оцени основания суждений о пригодности данных для заявленного сценария. Не подменяй неизвестное качество ни оптимизмом, ни обвинением в непригодности. Отдельно рассматривай состояние исходного материала, результаты проверок и планы исправления. Качество текста ответа модели относится к другим разделам.

## Извлечение по чек-листу
- `data_quality.condition`: найди сведения о полноте, актуальности, противоречиях, дубликатах, пропусках и известных дефектах. Сохрани затронутые источники и область дефекта. Для базы знаний различай устаревший факт, отсутствие ответа и несколько несовместимых нормативных версий.
- `data_quality.verification`: найди выполненные проверки, их охват, результаты и ответственного за поддержание качества. Отдели автоматическую проверку структуры от экспертной проверки смысла. Будущую очистку и обещанную валидацию сохрани как планы, не как уже выполненную работу.

Для каждого результата проверки сохраняй условия: версия данных, выборка, период, правило. Если сказано «проверили 800 показателей» без результата и критериев, извлеки ровно это утверждение; не делай вывод, что все показатели корректны. Опыт проверки другого продукта не подтверждает состояние текущего источника.

## Заключение
`satisfied`: приведены основания оценить пригодность существенных данных и известные ограничения. `not_satisfied`: зафиксированный дефект прямо нарушает конкретное требование сценария, например источник не содержит обязательный идентификатор для операции. `insufficient_data`: авторы заявляют качество без проверок или не определяют влияние известного дефекта. `not_applicable`: конкретная характеристика не относится к выбранному типу данных; не объявляй весь раздел неприменимым для текстовых документов.

## Ложные срабатывания и вопросы
Наличие data quality пайплайна не доказывает отсутствие содержательных ошибок. Успешная загрузка файла проверяет читаемость, а не актуальность. Несколько версий инструкции допустимы, если определено правило выбора действующей. Вопросы: «Какая проверка подтверждает заявленную актуальность?» и «Что делает система, если два источника дают несовместимые ответы?» Не превращай найденный дефект в обязательную полную очистку всей базы без связи со сценарием.

## Синтетические примеры — не данные проекта
Положительный: «Перед экспериментом эксперт сверил действующие версии регламентов; архив исключён из входа». Есть конкретная проверка актуальности.
Отрицательный: «Данные очистим перед запуском». Это план; текущая пригодность остаётся неизвестной.
