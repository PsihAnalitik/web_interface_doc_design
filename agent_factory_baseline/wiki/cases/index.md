# Реестр кейсов

Канонический список — registry.json в этой директории. Статусы: documented — описанный наблюдавшийся результат с основанием и границами; draft — ещё не проверенный материал; synthetic — учебный пример. Только documented автоматически добавляется в источники прогона с ролью case и source_id K_<id>. Статус не является независимой экспертной сертификацией.

- [Проход графа анализа собственного документа](factory-run.md): наблюдавшийся технический результат, не доказательство качества анализа или успешного внедрения у заказчика.
- [Шаблон нового кейса](template.md): заполняется подтверждаемыми сведениями, не выдуманными достижениями.

## Как добавить кейс

Создай Markdown по шаблону, укажи источники результата и ограничения переноса. Добавь в registry.json запись id, path (от корня wiki), status и fields с существующими field_id. До проверки держи draft. Используй documented только для сведений, которые команда готова подтвердить. Агент не загружает внешние ссылки сам.

wiki_search помогает найти аналог; wiki_get — прочитать условия. Для использования факта в заключении найди соответствующий K_<id> в источниках, затем приведи строковую ссылку. Draft и synthetic не являются доказательствами. Кейсы не становятся требованиями нового проекта и не доказывают опыт его команды. Для repeat_deployment нужны отдельные свидетельства team.

## Граница использования кейса

Факт кейса относится к проверке, если одновременно известны его исходный результат, условия получения и связь с конкретным свойством рассматриваемого компонента. Извлеки, что выполнено, кем, на каких данных/контуре, как проверено и что не проверялось. При неполноте сохрани известный результат и неизвестную переносимость; не дополняй недоступные приложения. Статус documented разрешает использовать переданный источник, но не расширяет границу его вывода.

## Граничные примеры — не данные проекта

1. «В источнике case зафиксирован completed и валидный JSON». Можно обосновать технический проход в названных условиях; нельзя из него вывести полезность замечаний. Разделяющий признак — что именно проверялось.
2. «Чужая команда измерила полноту поиска на договорах, наши входы — те же виды договоров с другими условиями доступа». Можно рассмотреть аналог с неизвестной переносимостью. Нельзя присвоить опыт нашей команде или перенести разрешения на документы.
3. «Учебный synthetic-пример показывает успешную интеграцию». Это иллюстрация правила, не факт выполненной интеграции. Сходство задачи не меняет статус источника.
4. «В documented-кейсе есть ссылка на отчёт, сам отчёт не передан». Известно утверждение автора и наличие ссылки; её содержимое не прочитано. Нельзя цитировать придуманный результат отчёта.
5. «Кейс принадлежит нашей команде, но работал только в облаке; текущий контур строго локальный». Собственный опыт относится к team_capabilities; достижимость в локальном контуре требует отдельного основания. Принадлежность кейса команде не снимает различие условий.
6. «В эксперименте метод не прошёл обязательную проверку». Это относящийся отрицательный результат при наличии источника. Не удалять его из аналогов только потому, что он не подтверждает успех; не делать из одного опыта доказательство невозможности всех подходов.
