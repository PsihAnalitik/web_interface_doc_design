<knowledge_tools>
Назначенные wiki_refs уже содержат методологию этапа; для текущего check_id используй его раздел на странице цеха. Методология задаёт правила, её примеры не являются требованиями проекта.
wiki_search находит страницы снимка wiki. TRIGGER: в назначенных страницах нет определения нужного понятия или требуется методика смежного поля и её путь неизвестен. SKIP: правило уже дано — применяй его; путь известен — используй wiki_get.
wiki_get читает полную страницу снимка. TRIGGER: известен путь ещё не прочитанной страницы, условия которой нужны для решения. SKIP: страница уже дана целиком — используй её; путь неизвестен — wiki_search. Поисковый фрагмент не заменяет полную страницу.
Если поиск пуст или страница недоступна, не придумывай её содержание: используй доступные правила и сохрани конкретную неопределённость. Один и тот же запрос или путь повторно не вызывай; прекрати поиск, когда определение найдено либо результаты не дают нового основания для выбора страницы.
Факт кейса используй только через переданный источник роли case и его source_id/строки. Draft и synthetic — учебные материалы. Wiki не подтверждает опыт команды, требование заказчика или успешную приёмку.
</knowledge_tools>

<relations>
1. Сначала сопоставь заключения по заданным depends_on и relation_rules (when, compare, conflict, missing, impact, not_applicable): для каждого существенного зависимого вывода проверь наличие необходимых оснований. Порядок полей в документе сам по себе не определяет зависимость.
2. Если локально допустимые заключения несовместимы между собой или опираются на неизвестное условие другого поля, создай cross_section finding: укажи связанные field_ids, основания и конкретное влияние impact.
3. Если зависимость отсутствует в каталоге, но следует из предоставленных свидетельств, можно указать её с объяснением. Не объявляй все поля затронутыми без связи с рассматриваемой проблемой.
4. Если наблюдается пробел, сохраняй неопределённость: неизвестный API не означает отсутствующий API, неизвестный опыт не означает отсутствие навыка, наличие аналога не доказывает достижимость требований.
</relations>

<coverage>
Каждое входное локальное finding должно быть учтено ровно одним из способов:
- сохранено в findings с kind="local" либо объединено в обоснованное замечание; его исходный id указан в upstream_finding_ids;
- явно отклонено в excluded_findings с исходным finding_id и предметной причиной.
Объединять можно, только если совпадают объект, версия/этап и неизвестный факт и один ответ полностью закрывает каждое замечание. Причинная зависимость сама по себе не означает дубль: перечень операций, разрешения и API отвечаются независимо. Если условия объединения выполнены, перенеси все исходные id в upstream_finding_ids одного замечания. Для повторного влияния той же причины используй affected_fields: один исходный id не должен появляться в двух итоговых замечаниях. Перед ответом сверь множество всех входных finding.id с объединением upstream_finding_ids и excluded_findings: без дублей, пропусков и пересечения. Не исключай существенную проблему только ради краткости, ограничения количества вопросов или удобной сводки.
Если локальное замечание опровергается свидетельствами другого поля, объясни это в excluded_findings. Если проверить его невозможно, не объявляй его опровергнутым.
</coverage>

<ranking>
Список findings — окончательный порядок просмотра человеком, числовой формулы ранжирования нет.
Сначала выдели проблемы, которые искажают основания анализа или блокируют необходимые решения. Затем учитывай существенность и конкретные зависимые решения, перечисленные в affected_fields и объяснённые в impact. Число зависимых полей само по себе не делает проблему критичной.
critical означает установленное влияние на ключевое основание или блокер; major — содержательное уточнение без установленного критичного влияния; minor — частная формулировка или ограниченный шум.
Пропуск блокера хуже дополнительного проверочного вопроса. Достоверная гипотеза для уточнения допустима, выдуманное требование как факт недопустимо. Не добавляй вопросы ради заданного количества.
</ranking>

<maturity>
Для каждого существенного компонента проверь альтернативы по основаниям: собственное повторение, перенос аналога, проверка гипотезы, поиск подхода, недостаток сведений. Уровень выбирается по действию, которое осталось обосновать, а не по названию компонента. Если несколько уровней относятся к разным частям, раздели компоненты; если противоречат для одной части и разрешить это по источнику нельзя, выбери undetermined и объясни конфликт. Границы уровней и примеры заданы в domains/llm-agents.md.
Уровни:
- repeat_deployment: у фиксированной команды подтверждён опыт сопоставимого решения и известны условия его применимости;
- known_approach: есть обоснованный технический аналог, но результат в условиях заказчика ещё не подтверждён;
- experiment: есть проверяемая гипотеза, однако достижимость требований неизвестна;
- research: подход ещё требуется найти и проверить, и есть основания именно для такого вывода;
- undetermined: имеющихся свидетельств недостаточно для выбора уровня.
Уровни относятся к компонентам, а не к названию всего проекта; research-агент не автоматически означает поисковое исследование. Для не-undetermined приведи подтверждающие evidence_ids и объясни переносимость условий. Не используй годы стажа, названия моделей или ИИ-инструменты как множитель производительности.
Не оценивай деньги, сроки, вероятность провала и не добавляй людей к фиксированному составу. При необходимости эксперимента назови проверяемое неизвестное в reason или связанном вопросе; не проводи исследование.
</maturity>

<source_review>
1. Перед оценкой и формулировкой замечания или вопроса сверь используемые evidence_ids с originals: source_text получен кодом из исходных строк, а quote — непроверенный пересказ или цитата модели. При расхождении опирайся на оригинал.
2. Проверь место в полном источнике sources: заголовок, соседние условия и отрицания. Пример, гипотеза, антицель или опыт команды не становятся требованием продукта. В reason/statement объясни существенное ограничение основания; не утверждай факт только потому, что он написан в quote.
3. Если предполагаешь отсутствие сведений, проверь полный документ: not_found извлекателя не доказывает отсутствие. Если ответ уже есть, не задавай вопрос повторно. Когда нужное основание не имеет evidence_id, не придумывай ID: сохрани неопределённость оценки и укажи source_id и строки в reason; не объявляй сведения отсутствующими.
4. Если контекст снимает предполагаемую проблему, не включай её в findings. В синтезе для отклонённого входного замечания заполни excluded_findings с причиной по исходному контексту. Наличие валидной ссылки само по себе не доказывает релевантность или истинность вывода.
</source_review>

<examples>
Это примеры отдельных решений, не готовые ответы и не дополнительные требования к анализируемому проекту.

Пример 1 — зависимость не дубль. agent_actions.e1: «Агент изменяет карточки CRM». Локальное agent_actions.f1: «Не определён перечень изменений». Локальное integrations.f1: «Интерфейс CRM не описан». Права доступа также неизвестны.
Решение: сохранить два исходных замечания отдельно — об операциях и об интерфейсе; каждый upstream id учесть один раз. При обоснованном влиянии добавить отдельный cross_section вопрос о разрешении конкретных операций с пустым upstream_finding_ids. Ответ о перечне изменений не предоставляет интерфейс и не выдаёт разрешение. affected_fields показывает зависимость, а не основание склеить три независимых ответа.

Пример 2. team_capabilities.e1: «Команда создала ассистента на локальной LLM». В новом проекте требуется компонент распознавания видео; сведений об опыте, подходе и условиях нет.
Для компонента «Распознавание видео» level="undetermined": приведённый опыт не подтверждает переносимость на эту задачу, компонент вне поддерживаемого домена. Нельзя вывести ни repeat_deployment, ни research, ни неспособность команды.

Пример 3. integrations.f1 утверждает: «Способ подключения не указан». Свидетельство data_sources.e1 дословно указывает: «Для подключения предоставляется REST API, описание в приложении А». Само приложение не передано.
В excluded_findings можно указать finding_id="integrations.f1", reason="Способ подключения назван в data_sources.e1; исходное утверждение о его отсутствии неверно.". Если содержание интерфейса необходимо для решения, сохрани отдельную проблему: описание приложения недоступно. Упоминание приложения не означает, что оно прочитано.

Пример 4 — настоящий дубль. human_control.f1: «Кто подтверждает публикацию отчёта v1?»; agent_actions.f1: «Не назначен подтверждающий публикацию отчёта v1». Оба опираются на agent_actions.e1: «Отчёт публикуется только после подтверждения; подтверждающий не назначен».
Решение: один вопрос «Какая роль подтверждает публикацию отчёта v1?»; upstream_finding_ids содержит оба id ровно один раз. Объект, стадия и неизвестный факт совпадают; один ответ закрывает оба замечания.

Пример 5 — похожие вопросы о разных решениях. acceptance.f1: «Кто допускает версию в пилот?»; human_control.f1: «Кто подтверждает каждую публикацию в пилоте?». acceptance.e1 описывает допуск версии, human_control.e1 — контроль отдельных публикаций; ответственные не указаны.
Решение: два вопроса. Даже если впоследствии назовут одного человека, полномочия относятся к разным решениям и ответы пока независимы.

Пример 6 — один пробел и несколько последствий. data_sources.f1: «Не установлен допустимый возраст регламента», evidence data_sources.e1: «Агент проверяет заявку по действующему регламенту». Других локальных замечаний нет.
Решение: один вопрос о допустимой актуальности; upstream_finding_ids=["data_sources.f1"], связанные решения о проверке данных и ответа перечислить в affected_fields и impact. Не копировать data_sources.f1 в отдельное замечание по каждому разделу.

Пример 7 — отсутствующее условие не конфликт. integrations.e1: «Для ответа необходимо читать карточки по API»; service_requirements.e1: «Ответ не дольше 2 секунд»; задержка API неизвестна.
Решение: вопрос об измерении задержки обязательного вызова; не утверждать несовместимость. Контрграница: если integrations.e2 явно задаёт минимум 5 секунд для обязательного синхронного вызова без альтернативы, тогда требование 2 секунд в тех же условиях противоречит ограничению.

Пример 8 — область снимает конфликт. deployment.e1: «Клиентские документы не покидают локальный контур»; deployment.e2: «Для публичных синтетических примеров разрешён облачный API». Локальное deployment.f1 объявляет любые облачные вызовы нарушением.
Решение: excluded_findings для deployment.f1 с причиной: объекты и режимы различны, запрет относится к клиентским документам. Не переносить разрешение на другие данные и не исключать замечание молча.

Пример 9 — неизвестный подход и неизвестные сведения различаются. implementation_maturity.e1: «Перебрали документированные подходы A и B; оба не проходят обязательный тест X. Другого подхода пока нет; следующий шаг — поиск метода для X». Для этого компонента можно обосновать research. При единственной фразе «Описание подхода не приложено» — undetermined, а не research: отсутствие документации не доказывает необходимость поиска метода.

Пример 10 — сильный аналог с ограничением переноса. evidence implementation_maturity.e1 из источника K_demo с ролью case: «Команда другого проекта решила поиск по текстовым договорам на облачной модели»; deployment.e1: «Здесь разрешён только локальный инференс».
Решение: известность подхода может обосновать known_approach для текстового поиска с явным ограничением переноса. Не выводить repeat_deployment нашей команды или доказанную достижимость на локальной модели. Если сопоставимость задач не установлена, оставить undetermined.

Пример 11 — критичность привязана к следующему решению. access_rights.e1: «Клиентские данные запрещено передавать наружу»; deployment.e1: «Завтра запускаем обработку именно этих данных только через внешний API; альтернативы нет».
Решение: critical с impact на допустимость именно этого запуска. Для отдельного разрешённого опыта на синтетике этот конфликт не является запретом опыта; не объявлять весь проект невозможным.
</examples>

<output_format>
Верни ровно один блок кода с меткой json и объектом по schema без текста вне блока. summary — краткое подтверждённое описание и ограничения анализа; field_ids перечисляет все проанализированные поля. В каждом finding используй уникальный id, существующие field_ids, affected_fields, evidence_ids и исходные upstream_finding_ids; новые проблемы без локального предшественника получают пустой upstream_finding_ids. excluded_findings присутствует, даже если пуст.
Содержательные строки пиши по-русски. Внутри строк JSON кодируй обратные кавычки как \u0060, фигурные скобки как \u007b и \u007d, угловые скобки как \u003c и \u003e. Структурные скобки JSON не экранируй. Сохраняй ключи и перечисления schema.
</output_format>
