# Baseline агентской фабрики

Реализация раздела 9 [дизайн-документа](../docs/document_design.md) поверх существующей `workflow_ai`. Запускается отдельно от Case Finder и веб-интерфейса.

В `passport.v0.1` — **18 полей, 36 проверок, 37 узлов**: для каждого поля отдельные извлечение и заключение, затем один агент проверки связей и приоритизации. Перечень полей конкретизирует черновик диздока и доступен для предметного ревью в [catalog.py](catalog.py). Семантические зависимости полей не задают порядок исполнения: фабрика пока выполняет граф последовательно.

```text
Текстовые .md (заказчик / команда / правила / кейсы)
  ├─ извлечение поля 1 → заключение поля 1
  ├─ извлечение поля 2 → заключение поля 2
  └─ извлечение поля N → заключение поля N
       ↓ все заключения и их исходные свидетельства
  проверка связей → упорядоченные замечания и вопросы
```

## Запуск

Нужен существующий checkout `workflow_ai` с подготовленным окружением Python **3.14+**, Pydantic 2 и OpenAI SDK. Проверенная ревизия фабрики: `40cb210493b01501bb795f295a021c72f58868bf`. По умолчанию `run.sh` использует соседний `../workflow_ai/.venv/bin/python`. Зависимости задаются окружением фабрики; отдельный движок или копия её исходников здесь не устанавливаются. При другом расположении задайте `WORKFLOW_AI_PATH` и, при необходимости, `WORKFLOW_AI_PYTHON`.

Из корня проекта:

```bash
./agent_factory_baseline/run.sh demo
```

Это **офлайн-демонстрация на записанных ответах**, а не запуск модели. Она проходит настоящий граф, проверки и сохранение артефактов. Использует только синтетические `examples/customer.md`, `examples/team.md` и `examples/replay.json`. Сеть и API-ключ не нужны; результат не является измерением качества LLM.

Подготовить конфигурацию и снимки своих документов без обращения к модели:

```bash
./agent_factory_baseline/run.sh plan \
  --document ./requirements.md \
  --team ./team.md
```

Запустить анализ моделью, явно указав её идентификатор:

```bash
# OPENAI_API_KEY задаётся в agent_factory_baseline/.env или окружении.
# OPENAI_BASE_URL задаётся для собственного OpenAI-совместимого endpoint.
./agent_factory_baseline/run.sh run \
  --document ./requirements.md \
  --team ./team.md \
  --model MODEL_ID
```

Системы на локальных LLM подключаются через тот же совместимый API. Вместо `--model` можно задать `BASELINE_MODEL`. Скопируй `.env.example` в `agent_factory_baseline/.env` и укажи `OPENAI_API_KEY`, `OPENAI_BASE_URL` и при необходимости `BASELINE_MODEL`. Python CLI автоматически загружает эти три настройки независимо от текущей директории и shell (включая Fish). `source` и `set -a` не нужны. Уже заданные переменные окружения имеют приоритет. Подстановка shell-команд и переменных внутри значений не выполняется. Настройки соседних проектов не читаются. `WORKFLOW_AI_PATH` и `WORKFLOW_AI_PYTHON`, если нужны, задаются в окружении до запуска скрипта. Команда `run` передаёт документы выбранному LLM-провайдеру; `plan` и `demo` этого не делают.

`--document`, `--team`, `--rules` и `--case` можно повторять. Роли источников сохраняются в контексте и результатах. При отсутствии профиля команды её возможности остаются неизвестными. Кейсы передаются явно: поиска по интернету и автоматического retrieval в этом baseline нет.

Дополнительные параметры: `--max-tokens` (8192 на ответ), `--max-iterations` (3 попытки узла), `--timeout` (300 секунд на обращение), `--output` (новая директория прогона). Выход по умолчанию: `agent_factory_baseline/runs/<время>-<id>/`. Существующую директорию нельзя перезаписать. Если модель не может вместить документ/результат, прогон должен завершиться явной ошибкой; автоматическое разбиение длинных документов не реализовано.

`--verdict-model MODEL_ID` назначает отдельную модель всем заключениям цехов и итоговому `synthesis`; `--model` остаётся моделью извлечения. Без этой опции все этапы используют одну модель. `--reasoning-effort none` явно отключает рассуждения через поддерживаемый провайдером параметр, одинаково на всех этапах; отсутствие опции сохраняет настройки провайдера по умолчанию. Поддержку отключения нужно проверять для выбранной модели.

```bash
./agent_factory_baseline/run.sh run --document docs/document_design.md \
  --model qwen3.7-plus --verdict-model qwen3.7-plus --reasoning-effort none
```

В `manifest.json` сохраняются `stage_models`, время завершения и длительность прогона. Для live-вызовов `calls.jsonl` дополнительно содержит `provider_responses`: фактическое имя модели, HTTP-статус, `finish_reason` и доступный `usage`, включая reasoning-токены. Метаданные сохраняются и для пустого ответа; отсутствие счётчика не означает нулевой расход. Заголовки авторизации, баланс аккаунта и текст рассуждений в эту запись не включаются. Запросы, обработка ошибок и повторы SDK остаются в существующем адаптере `workflow_ai`.

## Вход и проверка результатов

Принимаются непустые UTF-8 `.md`. PDF, DOCX, Markdown-изображения и встроенный медиаконтент отклоняются до обращения к LLM. Готовые интерпретаторы и сильные LLM используются для предварительной подготовки Markdown **вне этого модуля**. Здесь нет OCR, конвертера или загрузки ссылок. Потери преобразования нужно явно описывать в передаваемом тексте.

Извлекатель возвращает обязательную ссылку (`source_id`, `start_line`, `end_line`) и текст своими словами или цитату. Имя поля `quote` сохранено для совместимости; теперь оно означает **текст модели**, а не подтверждённую дословную цитату. Код проверяет источник и границы диапазона, но не совпадение формулировок. Неверный смысл при существующей ссылке — задача содержательной оценки, а не структурного gate.

Перед вызовами заключения и синтеза код подтягивает оригинал каждого свидетельства в `source_context.originals` и полный набор исходников с номерами строк в `source_context.sources`. Агент проверяет основания оценок, замечаний и вопросов по оригиналу и контексту (включая примеры, антицели, отрицания); предполагаемое отсутствие проверяется по полному документу. Полный контекст увеличивает входные токены. Это LLM-проверка в существующих узлах, а не отдельный независимый аудитор и не доказательство истинности выводов.

Отчёт отдельно показывает текст модели, ссылку на сохранённый источник и оригинальные строки, полученные кодом. Формат JSON не меняется; старые результаты и replay читаются без миграции, но смысл проверки `quote` изменён по согласованному требованию. Старые прогоны не переписываются.

Каждый пункт заключения имеет статус `satisfied`, `not_satisfied`, `insufficient_data` или `not_applicable`. Любой определённый статус, включая отрицательный и неприменимость, требует найденного свидетельства по этому пункту; без него допустим только `insufficient_data`. Проверяются покрытие чек-листа и ссылки на принятые извлечения.

Агент связей видит все заключения и извлечения. Каждое локальное замечание должно попасть в итоговую выдачу, объединиться с другим с сохранением исходных ID или быть явно исключено с причиной. Итоговый порядок задаёт агент с объяснением влияния на зависимые решения; произвольной формулы весов и обязательных 20 вопросов нет. Проработанность возвращается по компонентам; любой уровень кроме `undetermined` требует свидетельств, а `repeat_deployment` — также ссылки на сведения команды.

Проверка JSON и ссылок использует интерфейс `HITL` фабрики как **программный gate**, а не как подтверждение человеком. При ошибке возвращается `Revise`; цикл доработки и предел попыток исполняет `workflow_ai`. Предметное заключение — отдельный LLM-узел. Экспертной приёмки и автоматического доказательства истинности выводов нет.

JSON-транспорт обратимо экранирует спецсимволы внутри строк: текст с шаблонами `{{NAME}}` или обратными кавычками не ломает шаблонизатор/парсер фабрики. Ссылки проверяются после декодирования; оригинал берётся из сохранённого источника. Агентам доступны только штатные инструменты локальной wiki: `wiki_search` и `wiki_get`. Выполнение кода, запись в wiki и web_search не предоставляются. Фабрика использует локальный лексический поиск; если в окружении задан `BGE_M3_SERVICE_URL`, её штатный retriever обращается к указанному сервису эмбеддингов — это отдельная настройка окружения, которую нужно учитывать при работе с материалами.

## Предметная wiki и специализированные цеха

[Вход в wiki](wiki/index.md) · [Формат паспорта](wiki/passport.md) · [Методология связей](wiki/methodology/relations.md) · [Домен](wiki/domains/llm-agents.md) · [Реестр кейсов](wiki/cases/index.md).

Для каждого из 18 полей есть собственная страница `wiki/fields/<field_id>.md`: назначение и границы цеха, подшаги извлечения по двум check_id, критерии заключения, типовые ложные срабатывания, вопросы и помеченные учебные примеры. Общие шаблоны задают протокол ответа, а предметная специализация поступает через штатные `wiki_refs`. Оба агента цеха получают его страницу и применяют процедуру своей стадии; агент синтеза получает правила связей.

Wiki подключена штатными механизмами `workflow_ai`: страницы из `wiki_refs` автоматически входят в INPUTS, дерево доступно через `wiki_tree_root`, адресный поиск и чтение — через `wiki_search` / `wiki_get`. Не требуется отдельный поисковый сервис при стандартной локальной конфигурации. След вызовов инструментов сохраняется в `calls.jsonl` и нативном журнале фабрики.

Перед планированием/запуском весь набор копируется в `runs/<run>/wiki/`; у каждого wiki_ref версия `sha256:<digest>`. `knowledge.json` хранит хеши страниц, назначения узлам, правила связей, реестр кейсов и происхождение добавленных case-источников. Исходная wiki может изменяться после запуска, но агент читает снимок этого прогона. Отсутствующие страницы, некорректные реестры, пропущенные зависимости и запрещённые шаблонные маркеры отклоняются до вызова модели.

Свой набор задаётся `--wiki-dir /absolute/path/to/wiki`; это полный набор с той же структурой, не непроверяемая подстановка произвольного файла. Добавление кейса: создать Markdown по [шаблону](wiki/cases/template.md), указать подтверждения и ограничения, внести запись в `wiki/cases/registry.json` с id, path, status и fields. Только статус `documented` и совпадающие поля дают источник `K_<id>` с ролью `case`. `draft`/`synthetic` доступны как материалы wiki, но не доказательства проекта. Кейсы не подтверждают опыт команды: для него нужен источник `team`. Стартовый кейс описывает наблюдавшийся технический проход фабрики, **не успешное внедрение или доказанную точность анализа**.

Канонические 36 проверок и идентификаторы остаются в `catalog.py`; их читаемая версия `wiki/catalog.md` генерируется в снимке. Дополнять инструкции цеха можно в соответствующей странице, а изменение состава проверок требует обновления каталога и контрактных тестов.

## Методология связей и паспорт

`wiki/methodology/relations.json` содержит 33 правила, по одному на каждую зависимость каталога. Правило задаёт направление source → target, применимость, сравниваемые сведения, конфликт, обработку отсутствующего основания, влияние и неприменимость. Списки правил передаются в контекст соответствующих заключений и синтеза. Правила не задают порядок исполнения графа и не превращают отсутствие данных в автоматический блокер. Смысловая корректность их применения остаётся задачей модели и экспертной проверки.

`passport.json` имеет отдельную схему `project-passport.v1`, а `passport.md` — читаемое представление всех полей, проверок, пересказов, оригиналов, локальных заключений и принятого синтеза. Паспорт собирается кодом из принятых артефактов без дополнительной LLM. Состояния `not_processed`, `extracted`, `reviewed` показывают прогресс; они не означают соответственно «данных нет» или «эксперт одобрил». При сбое сохраняется частичный паспорт; `plan` создаёт пустой шаблон с каталогом. Это внутренний рабочий документ, не генерация ТЗ/ФТТ для заказчика.

Прежние `result.json`, `report.md` и JSON-контракты LLM сохранены; новые файлы добавлены рядом. Новая методология не переписывает старые результаты. Для отката можно запускать прежний код на новом каталоге прогона; данные не мигрируют.

## Артефакты

| Файл | Содержание |
|---|---|
| `passport.md`, `passport.json`, `passport.schema.json` | Читаемый паспорт, данные всех разделов и версия схемы |
| `knowledge.json`, `wiki/` | Снимок знаний, версии, назначенные страницы, реестр кейсов и правила связей |
| `report.md` | Внутренний отчёт: вопросы в порядке приоритета, влияние, проработанность, цитаты и локальные заключения |
| `result.json` | Типизированный паспорт, заключения цехов, итоговый анализ и статус прогона |
| `manifest.json` | Режим, модель и параметры, версия каталога, SHA-256 входов и конфигураций, ревизия фабрики, все связи графа |
| `sources/S*.md` | Снимки нормализованных исходников; номера строк цитат относятся к ним |
| `config/` | Точные промпты, схемы, настройки узлов и граф этого прогона |
| `calls.jsonl` | Все попытки вызовов: полный промпт, исходный ответ, usage и длительность |
| `validation.json` | Причины программного отклонения ответов |
| `factory.jsonl`, `artifacts/` | Нативный журнал и версии артефактов `workflow_ai` |

Фабрика сохраняет содержимое артефактов в файлах `vN.xml` независимо от формата; в этом процессе внутри находится JSON. `manifest.parents` фиксирует все предшествующие узлы, поскольку нативный `derived_from` хранит только одного. Сырые документы и ответы остаются в каталоге запуска; каталоги `runs/` исключены из Git. Они могут содержать чувствительные сведения.

При отказе провайдера или исчерпании доработок CLI возвращает ненулевой код. `result.json` помечается `failed`, итоговое заключение отсутствует, сохраняются проверенные частичные результаты и журнал. Код 0 означает завершение программных проверок, **не** экспертное одобрение проекта. Каждый повторный запуск создаёт новое хранилище; возобновления и миграции данных нет.

## Проверки

Из корня проекта, с окружением фабрики по умолчанию:

```bash
mkdir -p agent_factory_baseline/.checks
PYTHONPATH="../workflow_ai:$PWD" ../workflow_ai/.venv/bin/python -m pytest \
  agent_factory_baseline/tests -q \
  --basetemp="$PWD/agent_factory_baseline/.checks/pytest"
```

Тесты вызывают нативные wiki-инструменты и проверяют снимок/назначения всех 37 узлов, точное покрытие 33 зависимостей, отделение учебных кейсов и частичный паспорт. Также они проверяют ограничения входа, допустимость пересказа, извлечение оригинала, схемы и ссылки, перенос замечаний, различение опыта команды и аналогов, ограниченные доработки, сохранение отказов и полный офлайн-граф. Они не используют реальных клиентов или API-ключи.

Для оценки раздела 8 диздока нужны экспертная разметка и реальные модельные прогоны на отложенных документах. Журналы содержат основания для такой оценки, но семантические recall, ложная критика, качество приоритизации и согласие с экспертами автоматически не измеряются. Другие варианты сравнения — чек-листовый критик и вопросы без/с аналогами — остаются отдельными предшественниками. Этот модуль реализует вариант **«наши цеха»**.

## Границы изменения и откат

Изменения сосредоточены в этой директории; API, хранилище, веб-интерфейс Case Finder и исходники `workflow_ai` не изменяются. Откат не требует миграции: прекратить вызов нового CLI и сохранить нужные каталоги прогонов. Веб-интеграция и оценка коммерческих сроков/стоимости не входят в реализацию.

## Веб-интерфейс

Фабрика подключена отдельным режимом рядом с Case Finder. [Запуск сервиса, настройка моделей и сравнение](service/README.md). Для Docker соседний checkout `workflow_ai` не требуется: runtime поставляется в `vendor/workflow_ai`.
