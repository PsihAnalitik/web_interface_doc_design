# Репозиторий, CI и базовое развёртывание

## Сейчас

- Один GitHub-репозиторий: `web/`, `materials/`, `docs/` и `.github/`.
- CI настроен в `.github/workflows/ci.yml`: проверка синтаксиса, тесты, сохранение готовой статики как артефакта с SHA коммита.
- Сервер, домен и способ доступа ещё не выбраны. CD и внешние ресурсы не настроены; локальная подготовка CI не означает успешный запуск workflow на GitHub.
- Фронтенд подключён к `case-finder-main/server/`. Для анализа нужны API, worker, настроенные `API_USERS` и `OPENAI_API_KEY`, а также proxy `/api/` на том же origin. Одна статика позволяет открыть интерфейс и демопример, но не выполнить анализ.
- Вход в шапке выдаёт cookie `sid`. Пароль хранится только в памяти `web/server.mjs` и теряется при перезапуске процесса; состояние анализа, порядок вопросов и звёзды лежат в SQLite на volume `web_data`. Оригиналы документов для последующей оценки агентской фабрики копируются в volume `documents_archive` (`DOCUMENTS_ARCHIVE_PATH=/app/documents`) и не удаляются вместе с заданием. `make export-labels` собирает подтверждённую разметку в `exports/`.

## Рекомендованная первая поставка

Для текущего приложения достаточно Linux-сервера и Nginx, который отдаёт файлы из `web/dist/` по HTTPS. `web/server.mjs` предназначен для локальной разработки; запускать Node.js на сервере только ради этих статических файлов не требуется.

В качестве document root используйте отдельный каталог релиза приложения. Не отдавайте корень репозитория: в нём есть требования, прототипы и служебные файлы.

Backend уже находится в `case-finder-main/server/`; его Compose запускает API и worker с общим хранилищем. Следуйте [инструкции сервера](../case-finder-main/server/README.md). Reverse proxy должен снимать префикс `/api`: например, `/api/start_process` передаётся как `/start_process`, а query-параметр `mode=both` сохраняется. Передавайте Authorization и multipart body без изменений. Лимит размера body должен учитывать настройки API и накладные расходы multipart; тайм-аут — время загрузки и разбора документов. Basic Auth доступен пользователю только через HTTPS. Локальный аналог этого маршрута уже реализован в `web/server.mjs` через `API_URL`.

## Схема будущего CD

```text
pull request → проверки → merge в основную ветку
                            ↓
                    проверки того же коммита
                            ↓
                  артефакт copilot-web-<SHA>
                            ↓
                  deployment в production
                            ↓
                   проверка HTTP-ответа
```

Первый деплой лучше сделать вручную запускаемым (`workflow_dispatch`) из основной ветки. После проверки сервера можно включить автоматический деплой после успешного CI основной ветки. В обоих случаях разворачивается артефакт проверенного коммита, а не результат `git pull` в рабочем каталоге сервера.

Для production используйте GitHub Environment с ограничением разрешённой ветки; при необходимости добавьте ручное подтверждение, если оно доступно для выбранного тарифа и видимости репозитория. SSH-ключ и другие секреты храните в secrets этого environment. Данные подключения передавайте через variables. Не включайте секреты в фронтенд: любой файл из `web/dist/` доступен посетителю.

CD должен иметь отдельную concurrency group для production с `cancel-in-progress: false`: новый запуск не должен прерывать переключение текущего релиза. PR запускает только проверки, без доступа к production.

Для варианта с SSH:

1. Отдельный deploy-пользователь с доступом только к каталогу приложения.
2. Проверенный ключ SSH-хоста в known_hosts; не отключать проверку ключа.
3. Загрузка артефакта в новый каталог `releases/<SHA>`.
4. Проверка состава релиза, затем атомарное переключение ссылки `current`.
5. HTTP-проверка через домен. При неудаче — возврат ссылки на предыдущий релиз и повторная проверка.

Конкретные команды, права и HTTPS-конфигурация появятся после выбора сервера. Для подключения потребуются адрес, ОС, SSH-доступ, домен и решение о размещении API, worker и хранилища.
