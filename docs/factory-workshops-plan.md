# План доработки цехов анализа разделов документа

План основан на [валидации wiki от 7 октября 2026 года](factory-wiki-validation-2026-10-07.md) и сравнении результатов на документе о Критике. Цель — получать конкретные, обоснованные вопросы о недостающих решениях, сохраняя уже известные сведения, границы версии и независимость разных вопросов. Реализация этим документом не объявляется выполненной.

## Границы первой итерации

Сохраняются 18 полей паспорта, 36 `check_id`, 37 узлов, 33 зависимости, текущие JSON-схемы и внешний API. Первый шаг — перенести каталог из Python в Markdown цехов без изменения его содержания; затем основные изменения предполагаются в `wiki/fields/`, примерах существующих промптов и проверочных материалах. Ближайший образец — структура `wiki/fields/acceptance.md`: назначение, извлечение по check_id, оценка, ложные срабатывания, помеченные синтетические примеры.

Раздел цеха — смысловая область паспорта. Физический заголовок документа является контекстом свидетельства; один раздел паспорта может собираться из нескольких заголовков. Отсутствие заголовка «Приёмка» не доказывает отсутствия критериев. Приложение с чек-листом не считается полным описанием проекта только по названию файла.

В первой итерации не добавляются новый агент-разметчик разделов, новая поисковая система, обязательный RAG, обучение модели, кадровые рекомендации или заданное число вопросов. Общие корректные правила не дублируются во всех страницах wiki.

### 0 Перенести каталог в Markdown цехов

По уточнению пользователя определения `FIELDS` выносятся из Python. YAML frontmatter `wiki/index.md` задаёт `catalog_version` и упорядоченный список `fields`; frontmatter каждой `wiki/fields/<id>.md` содержит `id`, `title`, `depends_on` и список `checks` с `id`, `extract`, `evaluate`. Существующие предметные тексты сохраняются. `catalog.py` становится загрузчиком и валидатором; предметные изменения в дальнейшем делаются в страницах цехов.

Критерии завершения: проверка метаданных и связей до вызова модели; один каталог из снимка выбранной wiki для графа, gate и паспорта; изменение собственной wiki через `--wiki-dir` отражается в новом прогоне; веб-выдача читает названия из паспорта конкретного прогона. Для старых результатов без паспорта сохраняются идентификаторы, миграция не требуется. Сохраняются JSON-контракты и семантика 36 проверок. Этот шаг не заменяет предметную доработку B–D; готовность переноса подтверждается отдельными структурными и регрессионными проверками реализации.

Шаг 0 реализован 7 октября 2026 года: точное сравнение подтверждает сохранение всех определений и тел 18 страниц; полный набор `pytest agent_factory_baseline/tests -q` завершился с `116 passed, 1 warning in 2.06s` вне песочницы. Предупреждение относится к устаревающему алиасу AnyIO в Starlette. Внутри песочницы `TestClient` зависает до тела веб-теста. Независимое ревью закрыто после переноса веб-проверок в соответствующий тестовый модуль; изолированный `test_catalog.py` — `18 passed in 0.47s`. Шаги A–E этим переносом не реализованы.

Следующая итерация по запросу пользователя: B и предметная редактура C выполнены в трёх промптах этапов, 18 цехах и общей методологии. Для каждой из 36 проверок заданы принадлежность, исключения, атрибуты извлечения и неполнота; в цехах 185 граничных примеров. Отчёт и пределы проверки — в [review промптов](factory-prompt-review-2026-10-07.md). Полный набор регрессий: `116 passed, 1 warning in 3.16s`; это структурная часть D. Семантическая часть D и оценочный материал A не объявляются завершёнными: нового live-сравнения нет.

### A Зафиксировать оценочный материал

Для нового сравнения сохранить один и тот же подготовленный исходник и его SHA-256, роли приложений, версии кода/wiki, модели и параметры. Пять и сорок вопросов сохранить как наблюдавшиеся ответы, без объявления эталоном.

Если доступен серверный прогон, получить его `manifest.json`, `knowledge.json`, снимок источников/wiki, `result.json`, `passport.json` и принятые артефакты узлов. Для каждого спорного вопроса проследить: исходный фрагмент → извлечение → локальное замечание → объединение или исключение → пользовательская выдача. Если трассу получить нельзя, оставить причину старого результата неизвестной и начать воспроизводимое сравнение с текущей версией.

Эксперты размечают существенные неизвестности, уже отвеченные вопросы, неприменимые функции и допустимые объединения. Разногласия сохраняются и согласуются. Критерий готовности A: для каждого оценочного случая понятны исходные сведения, ожидаемые смысловые различия и запрещённые ложные предпосылки.

### B Согласовать объединение замечаний

Затронутые файлы: `agent_factory_baseline/prompts/synthesis.md`, при необходимости только поясняющие примеры `wiki/methodology/relations.md`, оценочные материалы.

Исправить пример со слиянием операций, прав и интерфейса. Сохранить положительный пример объединения двух замечаний об одном отсутствующем согласовании и отдельный отрицательный пример объединения согласования с документацией API. Поля `upstream_finding_ids`, `affected_fields`, `impact` и `excluded_findings` уже существуют; новые поля для этого не нужны.

Критерий приёмки B: ответ на один независимый вопрос не маскирует другой нерешённый вопрос; каждый исходный ID учтён ровно один раз. Права, доступность команды и технические аналоги не объединяются только из-за общей важности или соседства в документе. Число итоговых findings не фиксируется.

### C Уточнить процедуры существующих цехов

| Цех и страница wiki | Доработка | Что сохраняется | Проверяемый результат |
|---|---|---|---|
| `acceptance` | Для заявленных свойств ответа связывать требование, вид нарушения, проверочный случай и процедуру оценки. Добавить условные примеры педагогического/информационного агента | Общие два check_id; различие эксперимента и приёмки; запрет выдуманных порогов | Вопрос конкретизирует ложную критику, раскрытие решения и другие реально заявленные свойства, а не только просит «метрики качества» |
| `scenarios` | Примеры различения текущей версии, будущего развития и исключённых функций; обработка неполного контекста | Уже существующий учёт заголовков, отрицаний и антицелей | Будущий чат не становится обязательным для Baseline; нужное поведение при неполном входе не теряется |
| `data_sources` и `data_quality` | Примеры «документ и чек-лист есть, RAG исключён»; отдельно доступность, качество и пригодность для оценки | Разделение пользовательского входа, справочного корпуса и проверочного набора | Вместо «источники отсутствуют» вопрос уточняет только неизвестные состав, актуальность или достаточность |
| `agent_actions` и `human_control` | При необходимости примеры информационного ответа, запрета выдачи решения и исправления неверной критики | Различие генерации текста и изменения внешнего состояния | Не возникает выдуманного требования подтверждать транзакции у текстового Критика |
| `users` и `acceptance.procedure` | Контрастные примеры владельца, эксперта и утверждающего; допустимо подтверждённое совмещение | Имена не обязательны, если роль и полномочия ясны | Вопросы №1/5 либо разведены по решению, либо объединены при действительно одной неизвестности |
| `team_capabilities`, `team_availability`, `implementation_maturity` | Развести профиль исполнителей, авторов входного документа, опыт, доступность и переносимость аналогов | Фиксированный состав команды и запрет выводить производительность из стажа | Фамилии авторов не становятся доказательством компетенций; неизвестные опыт и время не скрыты одним общим вопросом |
| `service_requirements` и `deployment` | Регрессии на «за минуты», 24/7, нагрузку, размер документа и контур | Предметные правила уже достаточны; править только при подтверждённом сбое | Вопрос признаёт названную задержку и уточняет условия её измерения |
| `access_rights` | Регрессия на явно заданную или неизвестную внешнюю передачу документа | Не добавлять отраслевые запреты без источника | Тема не теряется при синтезе, когда она влияет на допустимость выбранного контура |
| `declared_unknowns` | Регрессии на отсутствующие приложения и предупреждения о потерях конвертации | Непрочитанное не считается проверенным | По одному приложению не утверждается отсутствие сведений во всём проекте |

`business_problem`, `current_process`, `expected_outcome`, `integrations` включаются в оценку связанных сценариев, но отдельная правка их wiki сейчас не обоснована. После переноса каталога в Markdown его состав и `relations.json` в первой итерации не расширяются: предметные уточнения укладываются в действующие проверки и связи.

Уточнения пишутся как общие различения с условием применимости. Сюжет Критика — проверочный пример, а не новая обязательная специализация всей фабрики. Учебные примеры для промптов следует строить на другом сюжете, чем отложенные проверочные документы.

### D Проверить структуру и семантику раздельно

Минимальная оценочная матрица:

| Случай | Обязательное различие |
|---|---|
| Полный критерий приёмки, процедура и ответственный уже заданы | Не задавать тот же вопрос заново |
| Свойство ответа заявлено, способ проверки неизвестен | Признать свойство; уточнить процедуру, а не объявлять все критерии отсутствующими |
| Требуется педагогическая критика | Сохранить проверку ложных замечаний и раскрытия готовых решений |
| Обычный справочный ассистент без педагогического ограничения | Не навязать запрет готового ответа |
| Неполный документ | Различить нехватку основания и доказанное противоречие |
| Критик должен проверять согласованность разделов | Уточнить, как будет проверяться эта способность продукта |
| Документ и чек-лист предоставлены, RAG отложен | Не требовать БЗ для текущей версии и не отрицать наличие входов |
| Чат предусмотрен позднее | Не блокировать Baseline отсутствием диалога |
| Факт расположен под неожиданным заголовком | Учесть его по смыслу и не объявить пропуск |
| Передано только приложение | Ограничить вывод доступным материалом |
| Названы авторы, профиль исполнителей отсутствует | Не отождествлять авторство и состав команды фабрики |
| Профиль команды есть, опыт и доступность описаны частично | Спросить об остатке; не объявлять команду неизвестной целиком |
| Эксперт и владелец различны или явно совмещены | Сохранить указанное различие либо совмещение |
| Две ссылки на одну неизвестность | Один итоговый вопрос с обоими upstream ID |
| Две разные неизвестности с общей зависимостью | Отдельные вопросы; связь через impact, а не потеря содержания |
| Локальное замечание опровергнуто полным источником | Обоснованное исключение; не повторять ложную предпосылку |
| Значимый пробел внешней передачи или нагрузки | Не потерять при объединении с контуром выполнения |

Структурные тесты проверяют неизменность схем, назначения wiki, ссылки, статусы и перенос идентификаторов. Replay проверяет обработку заранее заданных ответов, а не поведение модели. Для семантики нужны реальные ответы до и после изменения на одинаковом наборе, моделях и параметрах; сохраняются все попытки, включая неудачные.

Измерять по экспертной разметке: полноту существенных проблем, долю ложных предпосылок, повтор уже отвеченного вопроса, ошибочное включение будущего сценария и потерю независимой темы при объединении. Отдельно учитывать изменение приоритета и происхождение ошибки по этапам. Размер списка вопросов и наличие нужного слова не заменяют эти оценки.

Критерии завершения: все обязательные различия матрицы проверены; на размеченных случаях не осталось подтверждённых ложных предпосылок, повторов известных ответов и потерь обязательных тем; контракты проходят; ухудшения на отложенных документах разобраны до решения о применении. Численные пороги качества для всего домена согласуются отдельно после исходного замера — этот план не назначает их по одному документу.

### E Усложнять граф только при подтверждённой необходимости

**Если заключение регулярно находит в полном источнике сведения, пропущенные извлечением:** текущий контракт не позволяет выдумать новый evidence_id; сначала измерить частоту и влияние, затем спроектировать ограниченный возврат к извлечению с повторной валидацией. Известное ограничение описано в `prompts/verdict.md:52` и `validation.py:103–104`. Это отдельная работа с явным лимитом повторов, сохранением provenance и статуса частичного результата.

**Если ошибки систематически вызваны потерей границ раздела или версии:** рассмотреть карту диапазонов Markdown и метаданные области/стадии. Она должна поддерживать нестандартные заголовки, несколько источников и распределённые сведения; заголовок не должен становиться единственным маршрутизатором. Новые поля Evidence потребуют отдельного архитектурного решения: версии схем, совместимость replay, passport и веб-потребителей, миграция или чтение старого формата. До такого решения действующие модели не меняются.

**Если итоговая формулировка теряет независимые подвопросы несмотря на B–D:** отдельно рассмотреть представление групп вопросов. Сейчас несколько findings уже допустимы; изменение API не является первым средством исправления.

## Проверки и применение изменений

Базовая команда для wiki и ядра из корня репозитория:

```bash
PYTHONPATH="$PWD:$PWD/vendor/workflow_ai:$PWD/case-finder-main/server" \
  agent_factory_baseline/service/.venv/bin/python -m pytest \
  agent_factory_baseline/tests/test_catalog.py \
  agent_factory_baseline/tests/test_knowledge.py \
  agent_factory_baseline/tests/test_contracts.py \
  agent_factory_baseline/tests/test_runtime.py \
  agent_factory_baseline/tests/test_transport.py \
  agent_factory_baseline/tests/test_env.py -q \
  --basetemp="$PWD/agent_factory_baseline/.checks/workshops-plan-core"
```

Если реализация затронет API, worker или представление результата, дополнительно обязательны соответствующие веб-проверки; зелёное ядро их не заменяет. Для нового LLM-сравнения используют отдельные каталоги прогонов и сохраняют предыдущие снимки. Отложенная выборка не включается в доступные агенту wiki/case-источники.

Первая итерация обратима возвратом согласованной версии загрузчика, промптов и wiki; старые прогоны не переписываются и читаются по своим снимкам. Применение следующей версии допускается после структурной и содержательной проверки. Ни завершение графа, ни пять компактных вопросов сами по себе не означают прохождение приёмки.
