### 1. Problem definition

#### 1.1. Origin

The system, named CustomerAI audiences, is designed to simplify the process of creating customer audiences for marketers using the Twilio Segment platform. Currently, thousands of marketers use a sophisticated "Audience Builder" UI to define complex query logic for audience segmentation. This process requires users to navigate an advanced interface and have a deep understanding of their data assets.

The core problem is to enable marketers to create these sophisticated audiences using simple, natural language prompts, thereby abstracting away the complexity of the UI and the underlying data structures.

#### 1.2. Relevance & reasons

The existing workflow, while powerful, presents a barrier to entry for some marketers. An LLM-based solution that translates natural language to audience definitions would democratize this capability. The business impact of the initial implementation has been significant:
- A 3x improvement in the median time-to-audience creation.
- A 95% feature retention rate, conditional on the audience generation succeeding on the first attempt.

A key technical challenge is evaluating the correctness of the generated audience definitions. The audience logic is compiled into an Abstract Syntax Tree (AST), and a single natural language prompt can have multiple, semantically equivalent but syntactically different, correct AST representations. This makes traditional evaluation methods like string matching ineffective. The "LLM-as-Judge" system was developed to solve this evaluation problem.

#### 1.3. Expectations

The primary expectation is to provide a "magical" user experience where marketers can generate complex audiences and customer journeys from a simple prompt. The system must reliably convert natural language into a correct AST that the backend can execute.

The evaluation system (LLM-as-Judge) is expected to provide a reliable "scoreboard" to guide development and iteration on the generative AI system. This includes decisions on:
- Model selection (e.g., Anthropic Claude vs. OpenAI GPT).
- Prompt optimization.
- The impact of adding new components like RAG (Retrieval-Augmented Generation) or persistent memory.
- Architectural choices, such as single-stage vs. multi-stage LLM approaches.

#### 1.4. Previous work

The existing system is the "Audience Builder," a sophisticated UI that allows users to manually construct audience logic. This UI compiles the user's inputs into an AST, which is then used to segment users. The new LLM-based system is an alternative, simplified front-end to this existing infrastructure.

#### 1.5. Usage volumes and patterns

Thousands of marketers use the Twilio Segment platform daily to build audiences.

### 2. Goals and anti-goals

#### 2.1. Goals

- **Primary Goal**: To simplify audience creation by allowing marketers to use natural language prompts instead of a complex UI.
- **Evaluation Goal**: To create a robust, automated evaluation system (LLM-as-Judge) that can accurately assess the quality of LLM-generated ASTs.
- **Evaluation System Accuracy**: The LLM-as-Judge system must achieve high alignment with human evaluators. The system has achieved over 90% alignment.
- **Iterative Improvement**: Use the evaluation system as a scoreboard to systematically improve the generative model through prompt engineering, model selection, and architectural changes.

#### 2.2. Anti-goals

- **Avoid Heuristic-Based Evaluation**: The system is explicitly designed to avoid defining a "strict set of heuristics" for evaluation, as this is brittle given the unbounded set of correct AST answers.
- **Avoid Continuous Scoring**: The system avoids asking the LLM judge for a continuous score (e.g., 0-100), as LLMs tend to provide discrete values. A discrete 1-5 scale is used instead.

### 3. Risks and constraints

- **Technical Constraint (Output Ambiguity)**: The primary technical constraint is that a single audience description can be correctly represented by many different ASTs. This makes direct comparison for evaluation difficult. For example, "Customers who have purchased at least 1 time" and "Customers who have purchased more than 0 times" can result in different but semantically identical ASTs.
- **Data Constraint (Missing Labels)**: The initial dataset consisted of a large number of ground-truth ASTs generated by users via the UI, but it lacked the corresponding natural language prompts. This required creating a synthetic dataset for evaluation.
- **Risk of Incorrect Generation**: The main risk is the LLM generating an incorrect or semantically different AST from the user's prompt, leading to flawed audience segmentation and negatively impacting marketing campaigns. The LLM-as-Judge system is the primary mitigation for this risk during development.

### 4. Metrics and loss functions

#### 4.1. Offline metrics

- **LLM Judge Score**: A discrete 1-5 point scale used by the LLM Judge to score the quality of a generated AST against a ground-truth AST.
    - 1: "very bad"
    - 5: "perfect"
- **Alignment with Human Evaluation**: The percentage of cases where the LLM Judge's score aligns with a human expert's judgment.
    - The system achieved >90% alignment.
    - Using Chain of Thought (CoT) reasoning improved this alignment from ~89% to ~92%.

#### 4.2. Online/business metrics

- **Median Time-to-Audience Creation**: Measures the efficiency gain for users. The system achieved a 3x improvement.
- **Feature Retention Rate**: A proxy for user satisfaction and success. The feature has a 95% retention rate if the initial generation is successful.

### 5. Data (Dataset)

#### 5.1. Data sources

The primary data source is a collection of "Real World AST Input from End users." These are ASTs (represented as JSON-like objects) created by customers using the existing Audience Builder UI and serve as the ground truth for evaluation.

#### 5.2. Labeling strategy

A key challenge was the absence of natural language prompts corresponding to the existing ground-truth ASTs. To create a complete evaluation dataset of `{prompt: AST}` pairs, a synthetic data generation process was implemented:
1.  An **LLM Question Generator Agent** was built.
2.  This agent takes a ground-truth "Real World AST" as input.
3.  It outputs a synthetic natural language prompt that a user might have used to generate that AST (e.g., "Customers who have purchased at least 1 time").
4.  This process creates the necessary `{synthetic_prompt: ground_truth_AST}` pairs for the evaluation set.

### 6. Validation schema

The validation of the `LLM AST Generator Agent` is performed using the LLM-as-Judge framework. This framework serves as the core evaluation and validation pipeline.

The process is as follows (see image: `ml-design-doc-reviewer/data/raw_documents/images/case_056/img_006.webp`):
1.  **Input**: A "Real World AST Input" (ground truth) is selected from the dataset of customer-created ASTs.
2.  **Prompt Synthesis**: The `LLM Question Generator Agent` generates a synthetic user prompt from the ground-truth AST.
3.  **AST Generation (Test)**: The synthetic prompt is fed into the `LLM AST Generator Agent` (the system under test), which produces a `Generated AST`.
4.  **Judging**: The `LLM Judge Agent` receives both the `Generated AST` and the original `Real World AST Input`.
5.  **Scoring**: The Judge compares the two ASTs for semantic equivalence and outputs a score on a 1-5 scale, along with a Chain of Thought explanation for its reasoning.

This schema is used to score and compare different versions of the generator agent, including different underlying models, prompts, or auxiliary components like RAG.

### 7. Baseline solution

The baseline for the *evaluation system* was to define a "strict set of heuristics," which was deemed impractical. The LLM-as-Judge approach was chosen as a more flexible and scalable alternative.

For the *AST generation system*, the evaluation framework is used to establish baseline scores for different models. These scores serve as a benchmark for future iterations.
- **gpt-4-32k-0613**: Achieved the highest score of **4.55** out of 5.0.
- **Most potent Claude model**: Scored **4.02** out of 5.0.
- The similarity in scores between 8k and 32k context window versions of GPT-4 was noted, indicating method stability.

These scores provide a quantitative baseline to measure the impact of future changes, such as adding persistent memory via RAG or adopting new models.

### 8. Errors and their analysis

#### 8.1. Error taxonomy

The primary error is a semantic mismatch between the `Generated AST` and the ground-truth `Real World AST Input`. This means the LLM misinterpreted the user's prompt and created an audience with different logic than intended.

#### 8.2. Residual analysis and diagnostic approaches

- **Chain of Thought (CoT)**: The `LLM Judge Agent` is prompted to provide a step-by-step rationale for its score. This "Chain of Thought" is crucial for human developers to understand the judge's decision, debug the generator model's failures, and build trust in the automated evaluation process.
- **Impact of CoT**: Implementing CoT increased the alignment between the LLM Judge and human evaluators from approximately 89% to 92%.
- **Model for Judge**: OpenAI's `GPT-4` is used as the judge model. It was found that other strong models like `Claude 3 Opus` achieve similar performance as a judge, indicating alignment between different models on this evaluation task.

### 9. Training pipelines

The system does not involve training or fine-tuning LLMs from scratch. It is an agent-based system that relies on prompting pre-trained foundation models. The "pipeline" refers to the automated evaluation workflow.

#### 9.1. Evaluation Pipeline Architecture

The evaluation architecture consists of several interacting agents (see image: `ml-design-doc-reviewer/data/raw_documents/images/case_056/img_006.webp`):
1.  **Real World AST Input**: The ground truth from end-users.
2.  **LLM Question Generator Agent**: Generates a synthetic prompt from the AST.
3.  **LLM AST Generator Agent**: The production model being evaluated. It takes the synthetic prompt and generates an AST.
4.  **LLM Judge Agent**: Compares the generated AST to the real AST and provides a score and reasoning.

#### 9.2. Tooling

- **LLM Models**: OpenAI GPT series (e.g., `gpt-4-32k-0613`) and Anthropic Claude series (e.g., `Claude 3 Opus`).
- **Orchestration**: The team plans to explore orchestration frameworks like `AutoGen` for better coordination between agents in the future.

### 10. Features

This system does not use features in the traditional ML sense. The inputs are natural language and structured data (ASTs).

- **Input to `LLM AST Generator Agent`**: A natural language prompt from the user (or a synthetic prompt during evaluation).
- **Input to `LLM Question Generator Agent`**: A ground-truth AST (JSON-like structure).
- **Input to `LLM Judge Agent`**: Two ASTs for comparison: the `Generated AST` and the `Real World AST Input`.

Prompt engineering is a critical component, and "Prompt Optimization" is one of the key development activities enabled by the LLM-as-Judge framework.

### 11. Measuring results

#### 11.1. Offline evaluation methodology

The LLM-as-Judge framework is the primary offline evaluation methodology. It is used to run experiments and compare different configurations of the `LLM AST Generator Agent`.

**Experiment Example: Model Selection**
- **Hypothesis**: Different foundation models will have different performance levels for the AST generation task.
- **Method**: Run a set of evaluation examples through the pipeline, swapping out the model used in the `LLM AST Generator Agent`.
- **Results**:
    - `gpt-4-32k-0613`: **4.55 / 5.0**
    - Most potent Claude model: **4.02 / 5.0**
    - GPT-4 series performed slightly better than Claude 3.
- **Decision**: The scores provide a quantitative basis for model selection and serve as a baseline for future improvements. (see image: `ml-design-doc-reviewer/data/raw_documents/images/case_056/img_007.webp`)

### 12. Integration and Serving

#### 12.1. API design and integration

- **User Interaction**: The user provides a natural language prompt in the Audience Builder UI. (see image: `ml-design-doc-reviewer/data/raw_documents/images/case_056/img_003.webp`)

    2. The agent returns a generated AST.
    3. This AST is then processed by the existing Twilio Segment audience federation backend, which distributes the resulting user list to downstream marketing and sales tools.
