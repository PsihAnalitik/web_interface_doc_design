### 1. Problem definition

#### 1.1. Origin

As a financial institution, SumUp is subject to regulatory compliance for Anti-Money Laundering (AML) and performs transactional monitoring. This process involves machine learning models and rule engines whose outputs are verified by human risk and compliance agents.

When an agent confirms that an account has suspicious activity, they are required to escalate and report it to the corresponding authority by writing a financial crime report. This report, called "Reason for Suspicion," is a free-text narrative that outlines the observed behavior and provides supporting evidence from various sources, including ML model predictions, investigation notes, and verification processes.

#### 1.2. Relevance & reasons

The manual process of writing these financial crime reports is often repetitive and time-consuming. While most narratives follow a similar structure, they must be customized to reflect the specific typologies and behaviors of each case.

Generative AI, specifically Large Language Models (LLMs), presents an opportunity to significantly reduce the time agents spend on this task. The goal is to build an LLM-driven application to assist agents in generating these free-text reports, thereby optimizing the documentation of suspicious activity.

#### 1.3. Expectations

The system is designed as a human-in-the-loop tool to augment agent capabilities, not to fully automate the reporting process. The key expectation is to optimize documentation time without introducing the risk of automated, machine-driven false positives. Prior human confirmation and investigation of suspicious activity are considered paramount before the LLM application is used, as the consequences of an unverified automated alert are extremely high.

#### 1.4. Previous work

The existing workflow consists of risk and compliance agents manually writing the "Reason for Suspicion" reports. They synthesize information from multiple sources, such as:
*   Previous machine learning model predictions.
*   Investigation notes from linked cases.
*   Results from verification processes.

### 2. Goals and anti-goals

#### 2.1. Goals

*   **Primary Goal**: Save a substantial amount of time for risk and compliance agents in writing financial crime reports.
*   **Output Quality**: Generate high-quality, accurate, and coherent free-text narratives that are suitable for submission to authorities.
*   **Factual Accuracy**: Ensure the generated narrative accurately reflects the input data, including customer profiles, supporting facts, and conclusions, without inventing information.
*   **Structural Integrity**: The generated text must have an adequate structure, cover all relevant topics, and include a clear conclusion.

#### 2.2. Anti-goals

*   **No Full Automation**: The system must not operate as a fully automated reporting tool that files reports without human oversight.
*   **Avoid Automated False Positives**: The system should not be used to automatically raise alerts. It is only engaged after a human agent has confirmed suspicious activity.
*   **No Factual Invention**: The model must not hallucinate or invent facts, such as mentioning police reports or illicit activities not present in the source data.

### 3. Risks and constraints

#### 3.1. Risks

*   **Regulatory & Reputational Risk**: The high impact of a false positive (an incorrect automated alert) necessitates a human-in-the-loop design.
*   **Model Instability**: The LLM's output can be diverse, making it difficult to generate stable and comparable results across different runs.
*   **Subjectivity of Quality**: Language is complex, and multiple different narratives can be considered adequate, making objective evaluation challenging.
*   **LLM Biases**: Using an LLM as an evaluator introduces known biases:
    *   **Position Bias**: Tendency to favor the first result in a comparison.
    *   **Verbose Bias**: Preference for longer responses, even if they are less clear.
    *   **Self-enhancement Bias**: Preference for answers generated by other LLMs over human-written text.

#### 3.2. Constraints

*   **Application-Specific Evaluation**: The developed evaluation metrics are tailored to this specific application and cannot be used to compare performance across different projects.
*   **Human-in-the-Loop Requirement**: The system must be integrated into a workflow that includes mandatory review and confirmation by a human agent.

### 4. Metrics and loss functions

The primary focus of the project was to develop a reliable evaluation framework for the LLM-generated text, as traditional metrics were found to be insufficient.

#### 4.1. Offline metrics

##### 4.1.1. Traditional NLP Metrics (Considered and Rejected)

*   **Rouge Score (Rouge-1, Rouge-2, Rouge-L)**: This metric was used to measure the n-gram overlap between the generated text and a human-written reference text.
    *   **Rationale for Rejection**: The Rouge score showed minimal differences between accurately and inaccurately generated texts. It was deemed to have a narrow scope, focusing on semantic similarity while failing to assess broader context, text structure, presence of supporting evidence, or factual correctness. It is also heavily affected by paraphrasing.

##### 4.1.2. LLM-driven Evaluator

An LLM-based judge was developed to approximate human evaluation in a scalable way. This evaluator compares the LLM-generated narrative against a human-written reference text using a prompt that includes custom benchmark checks.

*   **Custom Evaluation Criteria**: The evaluator assesses the generated text against six specific criteria:
    1.  **Topic Coverage**: Ensures consistency between the topics in the generated and reference texts.
    2.  **Customer Profile Data**: Confirms the inclusion and correctness of customer data.
    3.  **Supporting Facts**: Checks for the presence of facts supporting the described suspicious behavior.
    4.  **Avoiding Invented Facts**: Verifies that no facts have been fabricated beyond what is in the reference text.
    5.  **Conclusion**: Ensures the generated text includes a conclusion.
    6.  **Text Structure**: Assesses if the narrative is clear, concise, and well-structured.

*   **Scoring Mechanism**:
    *   The LLM evaluator assigns a score from **0 (very poor) to 5 (excellent)** for each of the six criteria.
    *   It also provides a textual explanation for each score.
    *   A `general_score` is computed as the average of the individual scores.
    *   **Example (Good Text)**: Achieved a `general_score` of **4.67**.
    *   **Example (Bad Text)**: Achieved a `general_score` of **2.5**, primarily due to invented facts and lack of clarity.

*   **Calibration**: To improve objectivity and consistency, the evaluator is calibrated using **few-shot prompting**. This involves providing pre-labeled examples that exemplify a perfect "5" score, helping the model understand the scoring standard.

#### 4.2. Online/business metrics

*   **Agent Feedback**: During testing, human agents manually reviewed each LLM-generated narrative, providing comments and a numeric score. The correlation between these manual assessments and the automated LLM-driven evaluation was used to validate the effectiveness of the automated evaluator.
*   **Time Saved**: The ultimate business goal is to save agent time, though a specific metric for this was not detailed in the source.

### 6. Validation schema

#### 6.1. Train/validation/test split strategy

The validation approach does not follow a traditional train/val/test split. Instead, it relies on comparing model outputs against a set of reference texts.

#### 6.2. Evaluation Framework

1.  **Generation**: For a given case, the LLM application generates a "Reason for Suspicion" narrative.
2.  **Comparison**: The generated narrative is passed to the LLM-driven evaluator along with the corresponding human-written reference text for that same case.
3.  **Scoring**: The evaluator scores the generated text on the six custom criteria (topic coverage, profile data, etc.) and provides a quantitative score and qualitative explanation.

#### 6.3. Human Validation

The automated evaluation method itself was validated by comparing its outputs to manual reviews conducted by real agents. It was found that the automated evaluation was "on many occasions, closely related to the comments and scores provided by an agent," and the reasons for improvement highlighted by both methods usually matched.

#### 6.4. Leakage risks and mitigation

To mitigate biases in the LLM evaluator:
*   **Position Bias**: Mitigated by **position swapping**, where the order of the reference and generated texts is swapped during evaluation to ensure the model isn't biased towards the first input.
*   **Verbose & Other Biases**: Mitigated by **few-shot prompting**, which helps calibrate the evaluator by providing concrete examples of desired outputs and scoring.

### 8. Errors and their analysis

The custom evaluation criteria serve as a taxonomy for errors in the generated text.

*   **Topic Mismatch**: The generated text discusses topics not present in the reference (e.g., mentioning "police reports" when none existed).
*   **Data Inaccuracy**: The text includes incorrect data (e.g., mentioning "linked accounts" that were not in the source data).
*   **Fact Invention (Hallucination)**: The text fabricates information entirely. This is considered a critical failure. The inaccurate example scored a 1/5 on `check_facts_are_not_invented`.
*   **Unclear Narrative**: The arguments are not as clear as in the reference text, or there is repetition.
*   **Structural Flaws**: The text structure is confusing or deviates significantly from the required format.
*   **Missing Conclusion**: The narrative lacks a summary of suspicious activities or a concluding statement.

### 11. Measuring results

#### 11.1. Offline evaluation methodology

The primary measurement method is the LLM-driven evaluator, which provides:
*   A quantitative `general_score` (0-5) for rapid assessment.
*   A breakdown of scores across six qualitative dimensions.
*   A qualitative text explanation for each score, offering actionable insights for model improvement.

This allows data scientists to test model improvements rapidly without requiring manual review from agents for every iteration.

#### 11.2. A/B test design

A qualitative A/B test was conducted by having agents use the system.
*   **Hypothesis**: The LLM-generated narratives are high-quality and can be used by agents with minimal editing, thus saving time.
*   **Methodology**: An initial iteration was run where agents manually reviewed, commented on, and scored each LLM-generated narrative.
*   **Decision Criteria**: The results from the automated LLM evaluator were compared against the agents' manual feedback. The strong correlation between the two validated the automated evaluation approach and demonstrated the viability of the generated text.
